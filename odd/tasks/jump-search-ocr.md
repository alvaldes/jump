# jump-search-ocr

Objective: an opt-in OCR fallback for text search, for windows whose Accessibility text is missing or unusable (terminals, PDFs, images, canvases).
Branch: `feat/search-ocr` (from `main` 129030e, worktree `../jump-worktrees/search-ocr`) · Delivery: ask-on-risk · Test runner: `swift test --package-path Packages/JumpKit` (also in CI); latency from the app log.

## Specs

- S1 (user): "dale, arrancá con los tres (1,2,3) en worktrees separados" — item 3 was "OCR opcional para terminales, PDF e imágenes. Es más trabajo y necesita el permiso de Grabación de pantalla." Earlier approved: "OCR as an opt-in fallback … only for apps where Accessibility has no usable text" and "dale con solo Accessibility primero".
- S2: opt-in — a Settings toggle in the text search area, off by default, persisted. Turning it on requests Screen Recording; while not granted, Settings says so and offers to open the Privacy settings; search keeps working with Accessibility only.
- S3 (assumption, announced to the user): when enabled and granted, OCR of the target window runs in parallel with the Accessibility collection, started when the mode opens; it never delays the search box (< 50 ms target) or the main thread.
- S4 (assumption, announced to the user; refined after L6): for each query, matches come from Accessibility when it has at least one precise match; otherwise from OCR when it has any; coarse Accessibility matches (a text area without word bounds, e.g. a terminal buffer) are used only when OCR finds nothing. No merging or de-duplication between sources.
- S5: OCR matching follows the same rules (case- and diacritic-insensitive, reading order, Tab/Shift-Tab, statuses); OCR match frames are word-level boxes in AX coordinates (Vision normalized → window frame → global AX).
- S6: jumping to an OCR match clicks at its center with the hint modifiers (Shift right click, ⌘ double click, ⌥ move pointer); there is no caret placement for OCR matches.
- S7 (spike, `odd/tasks/jump-text-search.md` L2 and Engram `jump/text-search-spike`): use the legacy `VNRecognizeTextRequest` `.fast` (the Swift `RecognizeTextRequest` `.fast` returns almost nothing on macOS 27.0.1), capture at 2x (1x loses lines), cache or prefetch the ScreenCaptureKit window lookup (85–120 ms uncached); expected OCR ready ~50–125 ms after mode open.
- S8: Accessibility-only behavior is unchanged when the toggle is off (existing tests keep passing; add one proving it).

## Log

- L1 (2026-10-25): "dale, arrancá con los tres (1,2,3) en worktrees separados" (1 = text search fixes, 2 = jump-bench warnings, 3 = this OCR fallback). S3/S4 are the parent's announced interpretation of the approved "opt-in fallback".
- L2: Route: one writer (Writer trigger (a): runs in parallel with the fix/search-polish writer, independent behavior, several minutes each). Both touch Modes/TextSearchMode.swift and Search/**, so they use isolated worktrees and the parent merges.
- L3 (T1, writer): Design — OCR lines are `TextRun<ScreenText>` (node = word ranges + word frames in AX coordinates), matched by `ScreenTextLayout.matches`, which reuses `TextMatcher` and then gives each match the joined boxes of the words it touches (whole-word frames; line frame when Vision gave no word box). `TextSearchMode` takes an optional `ScreenTextSource` (`isEnabled`, `recognize`, `perform`); `nil` or disabled keeps the Accessibility path byte-for-byte (test compares both). Per query: Accessibility matches when there is at least one, else OCR matches; while Accessibility has none and OCR is still running the status stays "Searching…" (interpretation of S4/S5), then updates the current query when OCR lands. Recognition starts right after the box is shown and runs alongside `prepareApp`/collect; a dismissal cancels it and bumps a session counter so late results are dropped. OCR jumps go through `ScreenTextRecognizer.jump` → `ElementActions.click` at the match center (hint modifiers; no caret). `ScreenTextLayout.axFrame` converts Vision boxes (normalized, bottom-left) with the AX window frame; tested at 1x and 2x. Settings: `recognizeScreenText` (Bool, off; invalid → off); toggle in Settings under the shortcuts, `CGRequestScreenCaptureAccess` only when turned on, orange note + "Open Privacy Settings" while not granted; access re-read at every search and on app activation. Window list cached in `ScreenTextRecognizer`, reloaded on a miss (frame tolerance 4 pt) or a failed capture, prefetched at launch/when toggled on. Log category `search`: "OCR: window lookup … ms (cached), capture … ms (WxH), recognition … ms, n lines" and "OCR in App: n lines ready after … ms".
- L4 (T1, read-only probe, this process already had Screen Recording): Ghostty 1322x845 window: 46 lines, 314 word boxes; cold (list load) 306 ms, cached 103 ms; Xcode cached 66–79 ms, 36 lines. Word boxes from `.fast` are really word-level (e.g. 62 pt word in a 158 pt line). Finder/Zen focused windows were not in the on-screen window list (other Space) → `windowNotFound`, search falls back to Accessibility only. Gap: OCR ready ~70–100 ms after open when cached, ~300 ms cold; T2 measures live.
- L5: Merged onto fix/search-polish (four text search fixes). Conflict in TextSearchMode.dismiss resolved by keeping both. Interaction found while merging: the polish branch's pending Return resolved when Accessibility finished, so with OCR still running it was lost (and Return after Accessibility but before OCR was ignored). Fixed in 6401f69: a pending jump waits until the query has a final answer (`awaitsResults`: Accessibility still collecting, or no Accessibility match while OCR is still running) and resolves after either source finishes; tests `returnBeforeRecognitionFinishesJumpsOnceItDoes`, `returnDuringBothCollectionsWaitsForRecognition` RED → GREEN. 295 tests pass.
